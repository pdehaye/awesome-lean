# AeneasVerif/aeneas

- **Domain:** Verifying Rust programs. Rust's MIR (via Charon's LLBC) is translated into pure functional models for F*, Coq, HOL4 and Lean. This repo's Lean part is the Lean backend library and the Lean test suite.
- **Primary role:** `certifier-software`
- **Secondary roles:** `DSL-host/metaprogramming`
- **What the kernel checks:** Full proofs about the generated Lean models: hand-written files such as `tests/lean/Hashmap/Properties.lean` and the tutorial solutions. The trusted base includes axioms modelling unsupported Rust std items (`Aeneas/Std/Core/Atomic.lean`, `Fmt.lean`, `Target.lean`, and a slice spec axiom in `Aeneas/Std/Slice.lean`). There are 24 `sorry`s, which I did not locate individually.
- **Certified vs only expressed:** Functional-correctness properties of translated Rust (hashmap, AVL, BST, Curve25519 tests) are certified. The Rust-to-Lean translation itself is done by the OCaml tool and is not proven in Lean. The Lean side only receives its output.
- **Output artifact:** Theorems about Rust code, and a Lean standard library modelling Rust's `core`/`alloc`. A Lean executable writes `ExtractBuiltinLean.ml` for the OCaml tool.
- **Author mode:** Mixed human and machine: 108 test files begin "THIS FILE WAS AUTOMATICALLY GENERATED BY AENEAS". Proofs are human-written. I saw no LLM markers.
- **Translation direction:** Into Lean (Rust to Lean definitions). A small amount goes out of Lean: the `extract` executable emits OCaml listing the Lean std models.
- **Creative idea:** Lean is both the target and a source of metadata. Attributes such as `@[rust_fun "core::cmp::PartialEq::ne"]` on Lean models are harvested by a Lean executable into an OCaml table, so the extractor knows which Rust std functions have Lean counterparts.
- **Why Lean?:** Not stated; Lean is one of four backends. My assessment: the custom tactics (`step`, `scalar_tac`, `bvify`, grind integration) and Mathlib make the Lean backend the most automated one. That depends on Lean's metaprogramming more than on its logic.
- **Notable techniques:**
  - The `step`/`step*` tactic, which applies `@[step]` specs to monadic `let x ← f …` binds (`backends/lean/Aeneas/Tactic/Step/Step.lean`).
  - `rust_fun`/`rust_type` attributes and the `extract` executable (`backends/lean/Aeneas/Extract/Extract.lean`, `backends/lean/AeneasExtract.lean`).
  - Bounded scalar types (`U8`…`Usize`, `I8`…) with overflow-checked `Result` operations (`backends/lean/Aeneas/Std/Scalar/`).
  - Loop translation marked `@[rust_loop]` in generated code (`tests/lean/Hashmap/Funs.lean`).
- **Heuristic check:** The Phase 1 guess was `spec+proof + DSL/metaprogramming + computation/examples`. I agree on certifier plus metaprogramming. "Computation/examples" is weak: the high `example` count comes from tactic tests, not from running code.
